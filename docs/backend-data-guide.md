# Backend & Campus Data Development Guide

**Branch:** `feature/backend-data`  
**Owner:** Sk. Mohammad Maaz  
**Role:** Project Coordinator — Campus Data & Core Backend

## 1. Purpose of this branch

This branch builds the trusted campus-data and backend foundation used by every other module.

The frontend, navigation engine, AI layer, and testing work all depend on this branch producing clear, consistent data and stable APIs. Do not treat this work as only "entering room names"; it defines the data contract for the whole system.

## 2. Work to complete

### Campus data
Build structured data for:
- Blocks
- Floors
- Rooms
- Labs
- Staff rooms
- Library
- Canteen
- Seminar halls
- Main/secondary entrances
- Stairs
- Lifts
- Emergency exits
- Other important facilities

Each location should have a stable unique ID and enough information for search and navigation.

Suggested location fields:
`id`, `name`, `type`, `block`, `floor`, `description`, `aliases`, and optional coordinates/position data.

Connections should describe which locations can be reached from which other locations and the estimated travel cost/distance.

### Backend
Create a FastAPI service that can:
- return known campus locations;
- return location details;
- accept a source and destination;
- call the navigation service;
- return a structured route response;
- return useful validation errors;
- expose a health endpoint.

Do not put pathfinding logic directly inside route handlers. Keep API, data, and navigation responsibilities separate.

## 3. How to do the work

### Step 1 — Learn the data model
Before coding, draw the relationship:

**Campus → Block → Floor → Location**

and separately:

**Location ↔ Connection ↔ Location**

Understand why IDs and connections must be stable.

### Step 2 — Start with synthetic data
Use clearly labelled demo data until verified college information is available. Never invent actual room numbers or routes and present them as real campus facts.

### Step 3 — Define the schema
Choose a consistent JSON/Pydantic structure and document required versus optional fields.

### Step 4 — Implement backend modules
Keep responsibilities separated:

```
backend/
  app/
    main.py
    api/
    models/
    services/
```

The exact structure may evolve after the team reviews it.

### Step 5 — Validate
Test missing IDs, duplicate IDs, invalid floors, unknown locations, malformed requests, and invalid connections.

### Step 6 — Coordinate with other branches
The navigation branch consumes location and connection data. The frontend consumes API responses. Agree on the data/API contract before changing field names.

## 4. Tools to use

**Required**
- VS Code — development
- Git + GitHub — version control
- Python — backend language
- FastAPI — REST API
- Pydantic — request/response validation
- JSON initially — campus dataset
- pytest — backend tests

**Useful**
- Postman or Insomnia — API testing
- OpenAPI/Swagger UI generated by FastAPI — inspect API contracts

Do not add a database merely because it sounds advanced. Start with clean structured data; introduce SQLite/PostgreSQL only when the project actually needs persistent/admin-managed data.

## 5. AI-assisted development rules

Use AI to:
- explain FastAPI/Pydantic concepts;
- review a proposed schema;
- generate small code sections;
- suggest test cases;
- debug an error.

Before committing AI-generated code, explain:
1. What the code does.
2. Why the design was chosen.
3. What inputs it accepts.
4. What it returns.
5. What happens when the input is invalid.

## 6. Definition of done

A backend/data task is complete only when:
- the data structure is documented;
- the implementation works;
- invalid cases are handled;
- tests exist for important behavior;
- API responses are understandable;
- another team member can consume the interface without guessing;
- the owner can explain the code.

## 7. Commit style

Use focused commits such as:

```
docs: define campus data schema
feat: add campus location dataset
feat: create FastAPI location endpoints
test: validate campus data and API inputs
```

Do not mix unrelated frontend or navigation changes into this branch.
